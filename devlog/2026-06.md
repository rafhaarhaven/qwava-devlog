## 2026-06-14 — iOS: App Preview Video Fixed + v1.2.2 Submitted

### App Preview video fix
- Root cause confirmed: Apple requires a silent AAC stereo 48kHz audio track even for silent previews. Simulator recordings have no audio track at all, which Apple rejects.
- Additional issues in the source video: wrong color transfer (`iec61966-2-1` sRGB instead of `bt709`), variable frame rate (~44fps instead of constant 30fps), wrong dimensions (1206x2622 instead of 886x1920 for the 6.5" slot).
- Fix pipeline: decode source to raw YUV (`ffmpeg -c:v rawvideo`), re-encode with `fps=30,scale=886:1920`, `color_trc bt709`, then add silent track with `anullsrc=r=48000:cl=stereo`, codec `aac`, bitrate `128k`.
- Final command that worked: two-pass ffmpeg (raw intermediate + final encode with `-f lavfi -i anullsrc`).
- For future App Previews: always add silent AAC audio track. Use 886x1920 for 6.5" slot.

## 2026-06-17 — iOS: Your Space Rebuild + Play Stats Foundation + Shared Questions Store

### Decisions
- **Defined a "qualified play"** so most-played reflects real use, not opens. A deck counts as played when the session crosses any of: 60 seconds spent, 5 questions advanced, or deck finished. Chose OR (not AND) so a long single-question conversation, the deepest use of a conversation app, still counts.
- A session registers at most one qualified play (`playCounted` guard). Restart resets the session so a replay can re-qualify.
- **Share is recorded at "Continue to share"** in Natural Reach. That is the moment of intent and the last point observable before the OS share sheet; iOS does not report whether the share completed.
- `topDecks` / `recentDecks` filter to real decks *before* taking the top 3 / latest 6, so `quick_mix` and `favorite01` never occupy a slot (they have no Deck and were being dropped after the prefix, which showed only 2 cards).
- Deck card colors are pulled straight from the Deck (all hex in decks.json, verified across 50 decks) via a local `promoCard(for:)`, mirroring `buildPromoCards`. Only difference from the live cover: the deck number uses the title color.
- Concentric corners: image corner = card corner (24) minus the 4pt gap = 20.

### Data layer
- **New file `SharedQuestionsStore.swift`** (`Qwava/Data/`, Qwava target). `@MainActor` singleton, UserDefaults-backed (`SharedQuestionsStore.v1`), newest-first, deduped by question id (re-share moves to top with fresh timestamp), capped at 50. `SharedQuestion { id, deckKey, deckName, question, sharedAt }`. API: `record(...)`, `recent(limit:)`, `reset()`. Listens for `.qwavaResetAll`.
- **`PlayStatsStore.swift`**: added `@Published lastPlayed: [String: Date]` (deckID → last qualified play). `Snapshot.lastPlayed` is optional so existing saved data still decodes (no data loss on update). `registerPlay` now also stamps `lastPlayed`; `reset()` clears it; autosave `combineLatest` includes it. Added `recentPlayedDeckIDs(limit:)` (currently unused; the view computes directly). `defaultsKey` left at `v1` (see Unresolved).

## 2026-06-18 (session 2)

Two things this session: a content cleanup pass on question length, and a rebuild of the widget daily-question eligibility pool. No code touched; all changes are to questions.json (applied manually between batches) and to which questions carry the widget_eligible flag.

### Question shortening (wordiness pass)

Goal: bring down the longest questions so they read cleanly on the watch and the home-screen widget (both read the same questions.json). Earlier batches this week trimmed the absolute longest by rephrasing; this session focused on a safer, higher-volume approach: removing filler without changing meaning at all.

The recurring culprit is the opener "What's something that..." / "What's something you...", plus hedges like "that you think", "that you've", "actually", "really", "genuinely", and tails like "more than you'd expect". Stripping these is almost always lossless. Examples of the transform (not exhaustive):
- "What's something you do that..." becomes "What do you do that..."
- "What's something you learned about..." becomes "What have you learned about..."
- "Is there something you're carrying..." becomes "What are you carrying..."

Rules for shortening (apply to any future pass):
- Only shorten when meaning, depth, and vibe stay exactly the same. If a trim would change the nuance, leave it long or rephrase more carefully rather than forcing it.
- For genuinely long, complex questions, aim for a gentle 15 to 30 percent cut and land in the low 80s to low 90s; do not crush a deep question down to 60, it stops making sense.
- For wordy-but-not-complex questions, removing filler often gets 10 to 25 percent for free with zero meaning loss; prefer this.
- Written for the ear: it has to sound like one person asking another out loud. Read it aloud; if it trips, rewrite.
- No dashes of any kind (hyphens or em dashes). Reword or use commas.
- Plain language, accessible to non-native speakers. Banned words: boundary, energy (wellness sense), behavior/behave, trait, consumptive, unearned. A few of these turned up inside existing questions and were swapped out while shortening (for example consumptive to passive, social energy to socializing, behave to act, own energy to own rhythms). Worth a dedicated banned-word scan of the whole library at some point.
- Always verify each rewrite with a script before accepting: character count, percent reduction, banned-word check, dash check.

These same rules double as writing guidance: if new questions are written short, plain, and for the ear from the start, they will not need shortening later. A useful target when writing new questions is at or below the global average (low 70s), and ideally short enough that the longest word is not a display problem on the watch.

### Widget daily-question eligibility (the daily reflection pool)

Context: the widget and the Your Space daily question both show one question per day, chosen from questions where widget_eligible is TRUE, seeded by the date so everyone sees the same one each day. That pool had been frozen at 161 since it was first wired, while the library grew past 3,200, so newer questions were never candidates. This session we expanded and re-curated it toward 365 (one clean year, no repeats).

The selection rule, reconstructed and refined (use this whenever expanding the pool):
- Standalone: the question must make complete sense read cold, with no deck context, no partner across the table, and no setup. The mental image is a person with a free minute who opens their phone and reads one instead of doomscrolling.
- Universal: it must apply to almost anyone. Avoid anything assuming a job, career, startup, company, team, or networking context (a user might be a student or not working). Avoid place-locked wording (this city, here, in Lisbon) and relationship-specific wording (your sibling, your partner).
- Not time-bound: avoid wording tied to when it is read (this weekend, this week, tonight, this season, shorter days), because we do not know what day or season the user sees it. Evergreen "lately" or "recently" is acceptable since it works any day.
- Depth for reflection: favor medium and deep questions that invite a pause and a bit of self-reflection, since this is positioned as a mindful moment, not a party game. Keep a healthy layer of light and fun ones too so the daily prompt is sometimes a smile and not relentlessly heavy.
- Short and display-safe: keep length at or below the current eligible average and avoid very long words, so it never overflows the small widget surface.
- Spread across decks: cap how many come from any single deck so the daily rotation stays varied, and skip decks that are inherently context-locked (Lisbon, Berlin, Local Secrets, Sibling Stories) and the work-framed decks (Networking, Team Sync, Between Meetings, Startup Talk, Career Journeys) and the day or season specific ones (Weekend Debrief, Before the Weekend, The Long Days, The Quiet Season).

State after this session: eligible pool curated up to 365, with a mix that is roughly balanced between fun and serious and skewed light with a steady thread of medium and deep. The flag changes are applied to questions.json manually.

## 2026-06-21 — iOS: Firestore cloud sync for all four stores, sign-out clear, widget rename

Built cloud sync so a signed-in (registered) account keeps its activity across devices. Guests stay fully local and untouched. All code written here, pasted into Xcode manually. Prereq: added the FirebaseFirestore product to the Qwava target (FirebaseCore and FirebaseAuth were already linked).

### Model and decisions
- Sync only for real accounts. `AuthStore` never calls `signInAnonymously`, so guest = `user == nil`. CloudSync ignores anonymous users via an `isAnonymous` guard anyway.
- One document per user at `/users/{uid}`, with `schemaVersion` and modular sections: `playStats`, `favorites`, `savedQuestions`, `sentQuestions`. Additive only: never rename or remove a field, so future Connection Rhythm work (a recipient/contact dimension on sent records) can be added without data loss. All writes use `setData(merge: true)`.
- Merge is CRDT-style and idempotent, so repeated pulls never double count. playStats `playCounts` take the MAX per deck, `completedDecks` union, `lastPlayed` keep the latest. favorites union (decks and per-deck question ids). savedQuestions union by question id within each deck. sentQuestions union by id, keep the most recent `sharedAt`, newest first, capped at 50.
- Known tradeoff: cross-device play counts take the higher value, not the true sum. Fine for ranking On heavy rotation; true summation would need per-device counters. Parked.
- Firestore rules already correct (per-user, auth required): `match /users/{userId}/{document=**} { allow read, write: if request.auth != null && request.auth.uid == userId; }`. Region eur3.

### CloudSync.swift (new, Data/, Qwava target)
- `@MainActor` singleton, started once from `RootView.onAppear` via `start()`. Observes `AuthStore.$user`.
- On sign in: `pullAndMerge` reads `/users/{uid}`, merges each remote section into its local store, then pushes every section back up (so a new account's empty cloud gets seeded from existing local data on first run — this is the migration path for existing logged-in users, no separate step needed).
- `startPushing` subscribes to each store's published state, `dropFirst().debounce(1s)`, pushes the changed section. Per-section push methods return Bool.
- On sign out: `signedOut(previousUID:)` removes push subscriptions, does a final push so the cloud is current, and only then is local cleared (clear happens in the sign-out button, see below). If the final push fails (offline), local is kept so nothing is lost; it reconciles on next sign in.

### Store changes
- Each store gained `mergeRemote(...)` (additive union/max as above) and `clearLocal()` (wipe device copy only, never touches cloud). `clearLocal` is separate from the existing `reset()` (which fires on the global `.qwavaResetAll` preferences reset; SavedQuestionsStore's `reset` also rebuilds its autosave pipeline) so sign-out and preferences-reset stay independent.
- Files: `PlayStatsStore`, `FavoritesStore`, `SavedQuestionsStore`, `SharedQuestionsStore`.

### Sign out (MoreView)
- Race fix: the sign-out button flips auth and immediately routes to welcome, so the async CloudSync clear was losing to the navigation. Fix is to clear all four stores synchronously in the button before `router.route = .welcome`: `PlayStatsStore/FavoritesStore/SavedQuestionsStore/SharedQuestionsStore.shared.clearLocal()`. CloudSync still handles the final cloud push off the auth-state change.

Guest-mode paragraph unchanged (guests stay local). Website/App Store description copy ("No login. No setup.") left for the App Store build.
